# FairShift engineering report

## Repository audit

FairShift is a Next.js 16 App Router application written in TypeScript. It uses Tailwind CSS, Lucide icons, Zod, and Vitest. It has a Cloud Run-compatible Dockerfile and no configured external backend or identity provider.

The original project had a strong responsive presentation and seeded content, but attendance, safety, and administrative views were separate mock screens. There was no session provider, server API, database migration, persistent action history, or connected worker/admin workflow.

## Implemented in this iteration

- A typed, Zod-validated browser demo repository that keeps scenario data in short-lived `sessionStorage` and writes a local audit trail.
- A browser-hardening layer: per-request nonce CSP, HSTS, anti-framing and cross-origin controls, capability restrictions, no-store workspace responses, and no-index workspace metadata.
- Supply-chain guardrails: a production dependency audit gate, exact-install CI, Dependabot monitoring, and a documented private vulnerability reporting path.
- Connected attendance: check-in/check-out updates the worker shift UI, worker directory, dashboard attendance metric, and audit history.
- Connected safety workflow: a worker submits a validated report; it receives an ID, appears in the worker report list and admin command center, and staff can assign, progress, or resolve it with a required resolution note.
- Privacy boundary in the administrative incident view: anonymous reporter identity is stripped before rendering. The UI never shows an anonymous reporter name.
- Decimal-safe pay primitives, using integer paise for calculations and INR formatting.
- Clearer demo disclosures: local browser persistence is never described as centrally confirmed attendance or payroll.

## Architecture

```mermaid
flowchart LR
  W[Worker screens] --> D[Typed demo repository\nsessionStorage + Zod validation]
  A[Admin screens] --> D
  D --> R[Pay and fatigue rules]
  D --> L[Local audit log]
  P[Future production adapter\nSupabase/Postgres + RBAC] -. same contracts .-> D
```

The current deployment is deliberately a **demo-mode modular client application**. It persists only in the browser tab that performs the action, and the retained state expires after 30 minutes. It is not a substitute for server-side authorization, QR signing, encrypted file storage, organization isolation, or a real session service.

## Preserved functionality

The Apple-inspired responsive light visual system, high contrast/reduced motion fallbacks, opt-in read-aloud, 32 voice locales, core-worker language localisation, demo role entry points, safety categories, pay explanation, fatigue content, portable skill passport, Dockerfile, and Cloud Run deployment instructions remain in place.

## Production dependency plan

1. Add a Supabase or PostgreSQL adapter with migration-controlled organization, membership, attendance, pay rule, incident, feedback, credential, and audit tables.
2. Move every role check and mutation to authenticated route handlers; use RLS or equivalent organization scoping.
3. Integrate an approved auth provider for password recovery and verified phone/email onboarding.
4. Add signed expiring QR records, server-generated timestamps, idempotency keys, incident attachment storage, rate limits, and retry-safe queues.
5. Add Playwright end-to-end tests across production adapters before claiming multi-user synchronization or Cloud Run verification.

## Security verification

- `npm audit --omit=dev --audit-level=high` — fails the release gate if a high or critical production dependency finding is present.
- `npm audit --audit-level=moderate` — validates the full development and production dependency tree.
- Response-header smoke tests validate the nonce CSP, HSTS, anti-framing, cross-origin, permission, cache, and indexing policy on running production output.
- The `Quality and security` GitHub Actions workflow runs on every push and pull request; Dependabot checks both npm and GitHub Action dependencies weekly.

The nonce CSP is generated by the Next.js 16 `proxy.ts` convention. The proxy deliberately does not make authorization decisions; an edge proxy cannot replace server-side session verification and per-resource access checks.

## Verification

- `npm run test` — pay, fatigue, and anonymous-identity unit coverage.
- `npm run build` — production bundle check.
- Local HTTP checks cover landing, worker dashboard/pay/safety, and admin dashboard/workers/safety routes.

## Current limitations

- Browser-local demo state only; data is not shared between browsers, users, or Cloud Run instances.
- Demo sign-in is not authentication and must not be used for real worker data.
- QR scanning, downloads, speech recognition/recording, image attachment, full written translation for every voice locale, emails/OTP, and payments remain intentionally simulated or browser-dependent.
- No external deployment has been made or claimed.
